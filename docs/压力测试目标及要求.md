# 压力测试目标及要求

## 1. 文档目的

本文档用于明确潜艇视觉推理系统在正式部署前的压力测试目标、测试要求以及外接传感器接口规范。

压力测试的核心目的不是单纯验证系统“能够运行”，而是验证系统在长时间连续运行、推理负载波动、传感器异常、进程故障以及硬件异常等情况下，仍能够保持：

- 长时间稳定运行；

- 无内存和显存泄漏；

- 推理延迟处于可接受范围；

- 数据积压时能够主动背压和丢帧；

- 服务异常后能够自动恢复；

- 关键异常场景能够自动保存原始数据；

- 外部传感器数据能够统一、稳定地接入视觉推理系统。

---

# 一、压力测试目标及要求

## 1. 内存与显存泄漏检测

### 1.1 测试目标

验证视觉推理程序在长时间连续运行过程中不存在：

- CPU 内存持续增长；

- GPU 显存持续增长；

- 推理次数增加导致资源无法释放；

- 长时间运行后出现 OOM、CUDA OOM 或进程异常退出。

### 1.2 测试方法

编写独立压力测试脚本，模拟实际运行状态：

- 每 **2～3 秒执行一次完整推理**；

- 连续运行时间不少于 **24 小时**；

- 输入数据应尽量模拟真实摄像头数据流；

- 推理流程应覆盖正式系统中的图像预处理、模型推理、结果解析和日志写入等主要环节。

测试期间持续记录：

- GPU 显存占用；

- GPU 利用率；

- 系统内存占用；

- CPU 利用率；

- 主进程 PID；

- 推理次数；

- 单次推理耗时；

- 异常和错误日志。

推荐使用：

```bash
nvidia-smi
```

监控 GPU 状态，并使用：

```bash
htop
```

监控 CPU 和系统内存状态。

正式压力测试时，应将监控数据周期性写入日志文件，以便后续绘制资源占用曲线。

### 1.3 资源释放要求

每次完成推理后，代码中必须显式执行资源清理：

```python
import gc
import torch

torch.cuda.empty_cache()
gc.collect()
```

其中：

- `torch.cuda.empty_cache()` 用于释放 PyTorch 当前未使用的 CUDA 缓存；

- `gc.collect()` 用于主动触发 Python 垃圾回收。

### 1.4 验收要求

24 小时连续运行过程中：

- CPU 内存不得出现持续单向增长；

- GPU 显存不得出现持续单向增长；

- 不允许出现明显的阶梯式资源累积；

- 不允许出现 CUDA OOM；

- 不允许由于资源泄漏导致程序崩溃；

- 不允许随着推理次数增加而出现明显性能下降。

**任何微小但持续的内存或显存上涨趋势，都必须进行原因排查。**

---

## 2. 实时性边界与背压控制

### 2.1 测试目标

验证系统在正常负载和高负载状态下能够保持合理的实时性，并避免由于模型推理速度下降导致视频帧无限积压。

系统必须优先保证：

> 处理最新数据，而不是处理已经失去实时意义的历史帧。

---

### 2.2 端到端延迟统计

必须记录完整处理链路的端到端延迟：

```text
摄像头采集
    ↓
图像进入系统
    ↓
预处理
    ↓
模型推理
    ↓
结果解析
    ↓
传感器数据融合
    ↓
日志写入
```

定义：

```text
端到端延迟 =
日志成功落盘时间 - 摄像头帧采集时间
```

至少统计以下指标：

- 平均延迟；

- 最大延迟；

- P95 延迟；

- P99 延迟；

- 单次模型推理耗时；

- 队列等待时间。

其中 **P99 尾延迟**必须作为重点验收指标。

---

### 2.3 推理队列限制

推理请求队列必须设置明确的容量上限。

例如：

```text
最大积压帧数：10 帧
```

不得使用无限长度队列。

当新的视频帧持续进入，而推理速度暂时低于数据产生速度时：

```text
队列未满
    ↓
正常进入队列

队列达到上限
    ↓
丢弃最旧帧
    ↓
保留最新帧
    ↓
记录告警日志
```

推荐采用：

> **Drop Oldest（丢弃最旧数据）**

而不是丢弃最新帧。

原因是潜艇实时感知系统更关注当前环境状态，过旧的视频帧已经失去实时处理价值。

---

### 2.4 推理抖动检测

系统应持续记录模型推理时间。

当推理时间出现明显异常，例如：

- 连续多次超过正常推理时间；

- P99 延迟超过设定阈值；

- 推理队列持续接近满载；

- 单次推理时间突然大幅增长；

系统应产生告警。

必要时执行熔断或降级策略。

---

### 2.5 验收要求

压力测试过程中必须确认：

- 不出现无限队列积压；

- 不出现由于历史帧积压导致实时画面严重滞后；

- 超过队列容量后能够自动丢弃最旧帧；

- 每次丢帧均有日志记录；

- 能够统计平均延迟和 P99 延迟；

- 推理延迟发生明显异常时能够及时告警。

---

## 3. 进程守护与自愈机制

### 3.1 测试目标

保证系统即使在无人值守情况下发生软件或硬件异常，也能够：

```text
发现异常
→ 保存故障证据
→ 自动恢复服务
```

尽量避免潜艇任务执行期间因为单个进程异常导致整个视觉推理系统永久停止工作。

---

## 3.2 独立看门狗进程

必须部署独立于视觉推理主进程的 **Watchdog（看门狗）进程**。

看门狗至少监控以下三类状态。

### （1）主进程状态

检查视觉推理主进程 PID 是否仍然存在。

例如：

```text
主进程 PID 正常
→ 继续监控

主进程 PID 消失
→ 判定异常
```

---

### （2）日志心跳状态

主程序应持续生成运行日志或心跳记录。

看门狗检查：

```text
当前时间 - 最近一次成功日志时间
```

如果超过预设阈值，例如：

```text
10 秒
```

即使进程 PID 仍然存在，也应认为程序可能已经：

- 卡死；

- 死锁；

- GPU 推理阻塞；

- I/O 阻塞；

- 主线程失去响应。

此时触发异常处理。

---

### （3）GPU 状态

看门狗必须检测 GPU 是否仍然正常存在和可用。

需要识别：

- GPU 掉卡；

- NVIDIA 驱动异常；

- CUDA 无法访问；

- GPU 查询命令失败；

- 推理进程失去 GPU。

可以通过：

```bash
nvidia-smi
```

进行基础状态检查。

---

## 3.3 故障快照

任何异常发生后，在执行自动重启之前必须保存详细故障快照。

建议至少保存：

- 故障发生时间；

- 故障类型；

- 主进程 PID；

- CPU 使用率；

- 内存使用量；

- GPU 使用率；

- GPU 显存占用；

- `nvidia-smi` 输出；

- 最近若干条应用日志；

- 最近若干次推理耗时；

- 当前推理队列长度；

- 最近成功推理时间；

- 最近成功日志时间；

- Python 异常堆栈；

- 当前传感器状态。

故障证据不得因为服务重启而被覆盖。

---

## 3.4 自动恢复

完成故障快照保存后，看门狗应自动重启整个服务栈。

处理流程：

```text
发现异常
    ↓
保存故障快照
    ↓
停止异常服务
    ↓
清理残留进程
    ↓
重新启动服务
    ↓
进行健康检查
    ↓
恢复正常运行
```

---

## 3.5 防止无限重启

必须设计重启次数限制。

例如：

```text
短时间连续异常
    ↓
第一次自动重启
    ↓
第二次自动重启
    ↓
第三次自动重启
    ↓
停止自动重启
    ↓
进入故障状态并持续记录告警
```

不得出现：

```text
启动
→ 崩溃
→ 重启
→ 崩溃
→ 重启
→ 无限循环
```

否则可能进一步损坏日志、存储或系统环境。

---

## 3.6 验收要求

压力测试期间应主动模拟：

- 手动杀死主进程；

- 主进程卡死；

- 停止日志输出；

- GPU 查询异常；

- 模型推理异常。

确认系统能够：

1. 正确识别故障；

2. 保存故障快照；

3. 自动重启服务；

4. 重启后恢复正常推理；

5. 不发生无限重启循环。

---

# 4. 数据闭环存储策略

## 4.1 目标

视觉推理系统不仅负责实时输出结果，还应承担自动发现和积累高价值训练数据的功能。

系统运行过程中，异常和困难场景通常是未来模型优化最有价值的数据，因此必须实现：

> **异常场景自动保存机制。**

---

## 4.2 自动保存触发条件

至少包括以下两类情况。

### （1）模型低置信度

当模型输出结果的置信度低于预设阈值时，自动保存当前数据。

例如：

```text
模型置信度 < 阈值
    ↓
判定为困难样本
    ↓
保存原始数据
```

---

### （2）传感器数据突变

当外部传感器出现明显异常变化时，例如：

- 深度突然变化；

- 航向突然变化；

- 航速突然变化；

- 水温异常变化；

- 电池电压快速下降；

- 气体浓度异常；

- 舱底水报警；

自动保存当时的视频截图和传感器数据。

---

## 4.3 保存内容

一次异常事件至少保存：

```text
event_xxxxx/
├── image.jpg
├── sensor.json
├── inference.json
└── metadata.json
```

其中：

### `image.jpg`

保存未经压缩或尽量少压缩的原始摄像头截图。

### `sensor.json`

保存异常时刻对应的传感器数据。

例如：

```json
{
  "depth": 125.3,
  "heading": 182.4,
  "speed": 1.8,
  "water_temperature": 3.2,
  "battery_voltage": 47.6
}
```

### `inference.json`

保存：

- 模型输出；

- 标签；

- 置信度；

- 推理耗时；

- 模型版本。

### `metadata.json`

保存：

- UTC 时间；

- 本地时间；

- 任务编号；

- 摄像头编号；

- 软件版本；

- 异常触发原因；

- 数据文件关联关系。

---

## 4.4 黄金数据

这类自动保存的数据定义为：

> **模型迭代黄金数据。**

潜艇完成任务并靠岸后，应优先导出该批数据，用于：

```text
异常数据收集
    ↓
人工检查
    ↓
人工标注/修正
    ↓
加入高质量训练数据集
    ↓
模型再次微调
    ↓
重新部署
```

从而形成完整的数据闭环：

```text
实际运行
    ↓
发现困难样本
    ↓
自动保存
    ↓
人工标注
    ↓
模型训练
    ↓
模型升级
    ↓
再次运行
```

---

# 二、外接传感器接口清单

## 1. 定位与授时接口

### 1.1 水面 GNSS

潜艇处于水面状态时，通过 USB 接口连接 u-blox GNSS 模块，例如：

```text
u-blox NEO-M9N
```

Linux 系统部署：

```text
gpsd
```

守护进程。

GNSS 模块输出 NMEA 0183 数据流，由 `gpsd` 统一解析。

程序最终读取：

- 经纬度；

- UTC 时间；

- 对地速度；

- 定位状态；

- 其他可用 GNSS 信息。

建议程序层统一使用 JSON 格式数据。

---

## 1.2 水下定位/惯导

水下状态无法正常使用 GNSS，因此接入艇上惯性导航系统。

通信方式可采用：

```text
RS-232
```

或：

```text
RS-422
```

惯导系统可输出类似：

```text
$GPRMC
```

等 NMEA 语句。

相关串口数据同样接入 `gpsd` 进行统一处理。

---

## 1.3 软件接口统一

无论数据来自：

```text
水面 GNSS
```

还是：

```text
水下惯导
```

业务程序均统一从：

```text
gpsd socket
```

读取数据。

即：

```text
GNSS ──────┐
           │
           ├── gpsd ── socket ── 应用程序
           │
惯导系统 ──┘
```

这样可以屏蔽底层硬件差异，降低应用程序复杂度。

---

# 2. 姿态与环境传感器接口

## 2.1 航向

航向信息可从 NMEA：

```text
$HCHDG
```

语句中提取。

---

## 2.2 航速

航速信息可以从 NMEA：

```text
$GPVTG
```

语句中提取。

---

## 2.3 深度

深度采用压力式深度计。

推荐两种接入方式。

### 方案一：4～20 mA + PLC

```text
压力式深度计
    ↓
4～20 mA
    ↓
PLC
    ↓
Modbus TCP
    ↓
Linux 工控机
```

该方案适用于工业环境和长距离传输。

### 方案二：RS-485

对于本身支持数字输出的深度计，可以直接：

```text
压力式深度计
    ↓
RS-485
    ↓
Linux 工控机
```

---

## 2.4 水温、气压和湿度

可使用：

```text
BME280
```

等环境传感器。

接入方式包括：

```text
I2C
```

或：

```text
SPI
```

直接连接。

如果传感器距离工控机较远，也可以通过：

```text
传感器
 ↓
单片机
 ↓
USB 串口
 ↓
Linux 工控机
```

进行传输。

---

## 2.5 风速和风向

如果系统需要获取水面风场信息，可接入风速风向仪。

推荐解析 NMEA：

```text
$WIMWV
```

语句。

获取：

- 风速；

- 风向；

- 风速单位；

- 数据有效状态。

---

# 3. 平台状态传感器接口

## 3.1 电池状态

电池：

- 剩余电量；

- 电压；

- 电流；

- BMS 状态；

通过电池管理系统 BMS 的：

```text
CAN 总线
```

进行读取。

Linux 系统使用：

```text
SocketCAN
```

驱动进行统一访问。

整体链路：

```text
BMS
 ↓
CAN
 ↓
SocketCAN
 ↓
Linux 应用程序
```

---

## 3.2 推进器状态

推进器转速等运行数据统一接入：

```text
Modbus RTU
```

或：

```text
Modbus TCP
```

总线。

---

## 3.3 舱内气体浓度

舱内气体浓度传感器统一通过 Modbus 接入。

例如：

```text
气体传感器
 ↓
Modbus RTU/TCP
 ↓
Linux
```

---

## 3.4 舱底水报警

舱底水传感器或水浸报警器的状态统一接入：

```text
Modbus RTU/TCP
```

总线。

应用程序需要将其转换为明确状态，例如：

```json
{
  "bilge_water_alarm": false
}
```

---

# 三、传感器数据统一汇总

不同总线和协议的数据最终必须在应用层进行统一封装。

推荐统一为 Python 字典。

例如：

```python
sensor_data = {
    "timestamp_utc": "2026-08-10T07:30:21Z",
    "latitude": 3.123456,
    "longitude": 101.123456,
    "heading": 185.2,
    "speed": 1.7,
    "depth": 128.4,
    "water_temperature": 3.6,
    "air_pressure": 1012.3,
    "humidity": 65.2,
    "battery_percentage": 78,
    "battery_voltage": 48.1,
    "thruster_rpm": 1200,
    "gas_concentration": 0.02,
    "bilge_water_alarm": False
}
```

之后由系统统一注入 Qwen-VL 的提示词上下文。

整体数据链路：

```text
摄像头
    │
    ├───────────────┐
    │               │
    ↓               ↓
视觉图像        外部传感器
                    │
        ┌───────────┼────────────┐
        ↓           ↓            ↓
      gpsd      SocketCAN      Modbus
        │           │            │
        └───────────┼────────────┘
                    ↓
             传感器数据聚合层
                    ↓
              Python Dictionary
                    ↓
摄像头图像 ───→ Qwen-VL Prompt
                    ↓
                模型推理
                    ↓
             识别/分析结果
                    ↓
                  日志
```

# 四、传感器硬件安全要求

所有外部传感器与 Linux 工控机之间必须考虑电气隔离。

原则上：

> **所有外部传感器通信线路必须增加光电隔离或等效电气隔离措施。**

包括但不限于：

- RS-232；

- RS-422；

- RS-485；

- CAN；

- Modbus RTU；

- 模拟量输入；

- 外部 USB 转串口链路。

主要目的是防止：

- 电压浪涌；

- 地电位差；

- 电磁干扰；

- 外部设备故障；

- 瞬态高压；

通过通信线路直接损坏工控机。

对于 4～20 mA、RS-485、CAN 等工业接口，应优先使用具有隔离能力的：

- 隔离采集模块；

- 隔离串口转换器；

- 隔离 CAN 模块；

- 工业级 PLC；

- 浪涌保护器。

---

# 五、压力测试重点验收项目

正式压力测试完成后，至少需要确认以下项目。

| 编号    | 验收项目        | 验收目标             |
| ----- | ----------- | ---------------- |
| ST-01 | 长时间连续推理     | 连续运行 ≥ 24 小时     |

# 六、最终压力测试目标

本阶段最终需要证明：

> **视觉推理系统能够在潜艇实际运行环境中长时间、无人值守地稳定工作，并且在推理负载异常、资源异常、进程异常、GPU异常和传感器异常情况下具备明确的检测、记录、背压、数据保护和自动恢复机制。**

整个系统最终应形成：

```text
实时采集
   ↓
传感器融合
   ↓
视觉模型推理
   ↓
延迟与资源监控
   ↓
异常检测
   ├── 正常 → 持续运行
   │
   └── 异常
        ├── 保存黄金数据
        ├── 保存故障快照
        ├── 告警
        └── 自动恢复
```

即从单纯的“模型能够推理”，升级为：

> **能够长期运行、能够发现异常、能够自我恢复、能够积累数据、能够持续迭代的工程化潜艇视觉智能系统。**
