### 当前服务、日志与重启原则

| 服务 | 服务器监听地址 | 启动入口 | 日志 |
| --- | --- | --- | --- |
| 静态前端 | `127.0.0.1:19100` | `python -m http.server`，目录为 `frontend/` | `logs/development-frontend.log` |
| API | `127.0.0.1:9001` | `gunicorn --config deploy/gunicorn_api.conf.py deep_sea_explorer.production_wsgi:app` | `logs/development-api.log` |
| 语音 | `127.0.0.1:9009` | `gunicorn --config deploy/gunicorn_speech.conf.py deep_sea_explorer.production_speech_wsgi:app` | `logs/development-speech.log` |

- 重启前必须通过 `runtime/development-api.pid` 和 `ps` 核对 API 主进程；只允许重启确认属于本项目的 Gunicorn。
- API 重启会清空内存中的会话、memos、问答与未生成的报告素材；先结束当前监测并下载报告。
- 重启 API 时必须保留上节中的模型路径、离线变量、回环绑定和 `REPORT_FONT_PATH`。
- 服务器重启后，开发期服务不会自动恢复；按本节启动入口重新拉起前端、API、语音服务和本机 SSH 隧道，并重新验收。

### 禁止触碰的既有服务器资源

- `/projects/deepsea_vlm` 及其已有 Conda 环境。
- `/projects/deep-sea-realtime`、`/etc/deep-sea-realtime` 及其历史部署配置。
- 服务器 Apache、systemd、Nginx、系统包、CUDA 驱动、系统 FFmpeg 与 Mihomo 配置。
- 不恢复、不下载 SDXL；当前项目没有图片生成功能需求。

## 2. 当前运行拓扑

```text
本机浏览器 http://127.0.0.1:19100
  -> SSH 本地端口转发
  -> 服务器 127.0.0.1:19100  静态前端
  -> 服务器 127.0.0.1:9001   Gunicorn API
  -> 服务器 127.0.0.1:9009   Gunicorn 语音服务
```

- 所有开发服务仅监听服务器回环地址，不接管 Apache、Nginx、systemd 或其他既有项目。
- 图片生成功能明确关闭：`IMAGE_GENERATION_ENABLED=false`；不要下载或恢复 SDXL。

## 3. 本机入口和 SSH 隧道

使用已配置的 `deepsea-codex` SSH Host 建立三个本地转发：

```powershell
ssh -N -T -o BatchMode=yes -o ExitOnForwardFailure=yes `
  -L 127.0.0.1:19100:127.0.0.1:19100 `
  -L 127.0.0.1:9001:127.0.0.1:9001 `
  -L 127.0.0.1:9009:127.0.0.1:9009 `
  deepsea-codex
```

- 浏览器入口为 `http://127.0.0.1:19100/`。
- 验收时至少检查：首页返回 `200`、`http://127.0.0.1:9001/health` 返回 `status: ok`。
- 转发失败时先排查本机 `19100`、`9001`、`9009` 是否已被旧 `ssh.exe` 占用，再使用 `ssh -vvv` 确认实际 Host、私钥和服务端 key options。
- SSH 专用别名、私钥约束和服务器操作边界见 `docs/Codex服务器SSH使用说明.md`；不要在脚本或文档中写入私钥路径、密码或 Token。

## 4. 视频监测主链路

```text
摄像头 / 虚拟摄像头
  -> 前端采集 JPEG 帧（200 ms）
  -> 前端按 1 s 批量 POST /videoanalyze（X-Session-ID）
  -> VideoIngestionService 写入 MP4 会话片段
  -> MonitoringService 后台任务
  -> Qwen3-VL 描述视频 + 识别典型画面
  -> GTE 计算 memo 向量、去重并发布
  -> 前端轮询 GET /memos，显示中文监测文本和样本
```

- 前端实现位于 `frontend/index.html`，运行配置由 `frontend/runtime-config.js` 提供。
- API 路由包括 `/videoanalyze`、`/memos`、`/generate_report` 和 `/health`。
- Qwen 模型懒加载；健康检查的 `model_detail=not_loaded` 在首次推理前属于正常状态。
- 会话数据存于进程内内存。因此当前开发模式必须使用单个 API worker，重启 API 会清空当前会话、memos 和报告素材。

### 单帧兼容性

浏览器刚开始采集时可能只上传一张 JPEG。该 JPEG 被封装为单帧 MP4，而 Qwen3-VL 视频处理器至少需要两个时序帧。`QwenAdapter._video_frames()` 会在只读到一帧时复制该帧，保证前端协议无需改变。

相关代码：`src/deep_sea_explorer/infrastructure/models/local/adapters.py`。

## 5. PDF 报告

报告由 `ReportService` 汇总前端上报的 memos、聊天、样本和统计数据，再由 `ReportLabRenderer` 写入 PDF。

- 顶部元数据包含：报告生成时间、任务时间范围和任务会话。
- 页面包含：任务总结、生物统计/样本、环境统计/样本、动态监测日志、交互记录和统计附录。
- 前端只有在一次有效监测结束后才启用“生成任务报告”。

### 中文字体要求

服务器中的 `NotoSansCJK-Regular.ttc` 是字体集合，ReportLab 的 `TTFont` 不能直接加载。内置 CID 回退字体会造成数字、拉丁字符或部分中文缺失；Droid 回退字体也会遗漏部分汉字。因此开发部署必须显式指定完整的中文 TTF：

```text
REPORT_FONT_PATH=/projects/deep-sea-explorer-codex/app/runtime/fonts/simhei.ttf
```

- 字体文件仅作为服务器运行时资源，不能提交到仓库。
- API 启动时必须带上上述环境变量；否则可能重新出现标题、时间、图表标签或正文空白。
- 修改报告渲染后，使用 `pdftoppm` 将 PDF 逐页渲染为 PNG 做视觉检查，不能只依赖文本提取。
- 回归测试：

```bash
.venv/bin/python -m pytest tests/integration/test_report_service.py -q
```

## 6. 真实视频模拟摄像头

Chrome 的 `--use-file-for-fake-video-capture` 只接受 Y4M，不能直接传入 MP4。项目中的真实测试视频为：

```text
Actual_deep-sea_exploration_footage.mp4
```

当前已生成的运行时素材均被 `.gitignore` 忽略：

| 文件 | 规格 | 用途 |
| --- | --- | --- |
| `runtime/actual-deep-sea-camera-test.y4m` | 640x480, 60 秒, 10 FPS | 快速高分辨率冒烟测试 |
| `runtime/actual-deep-sea-camera-full.y4m` | 320x180, 5 分 31.5 秒, 10 FPS | 完整时长低空间测试 |
| `runtime/actual-deep-sea-camera-full-720p.y4m` | 1280x720, 5 分 31.5 秒, 10 FPS, 约 4.58 GB | 完整时长 720p 验收 |

可使用本机已有 FFmpeg 重新生成，例如：

```powershell
& 'C:\Program Files (x86)\EVCapture\ffmpeg.exe' -i .\Actual_deep-sea_exploration_footage.mp4 `
  -vf 'scale=1280:720,fps=10' -pix_fmt yuv420p -f yuv4mpegpipe `
  .\runtime\actual-deep-sea-camera-full-720p.y4m
```

启动隔离 Chrome 虚拟摄像头：

```powershell
.\scripts\start-video-camera-test.ps1 `
  -VideoPath .\runtime\actual-deep-sea-camera-full-720p.y4m `
  -Url http://127.0.0.1:19100/
```

脚本会使用独立 Chrome profile 并自动允许摄像头权限。打开页面后仍需手动点击“开始监测”。Y4M 近似无压缩，生成前必须估算磁盘空间；不再需要的测试流应由负责人确认后删除。

## 7. 开发与验收清单

1. 确认 SSH 隧道、前端首页和 API `/health` 正常。
2. 使用虚拟摄像头或真实摄像头开始监测，确认 `/videoanalyze` 成功且 `/memos` 出现中文结果。
3. 首次模型推理后检查 API 日志，不能出现 `temporal_factor` 单帧错误。
4. 结束监测并生成报告，逐页确认标题、时间、中文正文、图表标签、样本图片和页码均可见。
5. 执行针对性测试：

```bash
.venv/bin/python -m pytest tests/unit/test_local_model_runtime.py -q
.venv/bin/python -m pytest tests/integration/test_report_service.py -q
```

6. 修改服务端代码后，只重启已确认 PID 的独立 API Gunicorn；不要重启 Apache、既有 systemd 服务或其他项目。

## 9. Git 版本管理

当前代码以 GitHub 仓库 `https://github.com/EMC1901/deep_sea.git` 为远端协作源，本地与服务器均使用分支 `codex/development-server-baseline`。已验证的基线提交为 `f178148`（`feat: establish development server baseline`）。服务器应用目录 `/projects/deep-sea-explorer-codex/app` 已初始化 Git，并已导入该基线。

### 日常开发流程

1. 在本地修改代码和文档，运行对应测试并检查 `git status`。
2. 提交聚焦的变更：`git add <文件>`、`git commit -m "..."`。
3. 推送到 GitHub：`git push origin codex/development-server-baseline`。
4. 服务器更新前先备份或确认当前服务状态，再在服务器应用目录执行 `git fetch origin` 与 `git diff`，确认差异后再合并或切换版本。
5. 仅重启本项目中已确认 PID 的开发服务，并按本文件的入口清单验收。

服务器当前保留若干服务器专属文件改动（包括 `docs/` 中的运维资料、`frontend/index.html` 等），这些差异未经审核不得覆盖、提交或删除。`runtime/`、日志、模型缓存及测试产物由 `.gitignore` 排除；`docs/工作流.md` 也保留但不纳入版本提交。

### 服务器同步注意事项

- 服务器直连 GitHub 的 `git fetch` 可能因网络超时；本次采用本地生成 Git bundle、通过既有 SSH 通道传输，再在服务器导入的方式完成基线同步。后续遇到同样情况可复用该方式。
- 不得在运行中的服务器目录使用 `git reset --hard`、`git clean` 或无确认的覆盖式复制。若需要让服务器与 GitHub 完全一致，必须先单独确认服务器专属文件的处置方案。
- 提交前检查待提交文件，确保不包含 `.env`、Token、密码、私钥、模型权重、视频、日志、报告和其他运行时产物。
